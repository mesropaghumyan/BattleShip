- (direction) Fast path choisi par l'utilisateur; usage = substrat de build interne uniquement (pas de support de presentation)
- (decision) Paradigme: architecture en couches avec noyau de domaine isole (Domain Kernel + Thin Adapters). BattleShip.Models = domaine pur (entites de jeu + DTOs partages), zero dependance externe [ADOPTED, deja vrai dans le csproj existant]. BattleShip.API = couche application/adaptateurs (endpoints Minimal API, service gRPC, validateurs FluentValidation, store d'etat en memoire). BattleShip.App = presentation (composants Blazor, clients HTTP/gRPC-Web). BattleShip.Tests = adaptateurs de test (xUnit unitaire + integration via WebApplicationFactory).
- (decision) AD-1 Placement du noyau de domaine: le moteur de jeu (Grid, Ship, Shot, Game, GameEngine, IOpponentStrategy) et les DTOs d'echange vivent tous dans BattleShip.Models. Binds: CAP-1. Prevents: logique metier dupliquee/couplee au transport dans API ou App. Rule: BattleShip.Models ne reference aucun package NuGet ASP.NET/gRPC/FluentValidation, uniquement le BCL; toute dependance transport reste dans API/App.
- (decision) AD-2 Frontiere de visibilite: les endpoints HTTP et le service gRPC ne serialisent jamais l'entite domaine Grid brute; ils passent par un mapping dedie vers deux vues distinctes (vue proprietaire avec navires, vue adverse avec seulement touche/rate/coule). Binds: CAP-1, CAP-2, CAP-5, CAP-6. Prevents: fuite des positions de navires non decouvertes via une reponse API. Rule: un type de mapping (ex GameViewMapper) au niveau de la couche API est le seul point de conversion Domain -> DTO expose; un test verifie qu'aucune coordonnee de navire non coule n'apparait dans la vue adverse serialisee.
- (decision) AD-3 Proprietaire et concurrence de l'etat: une unique abstraction IGameStore (implementation en memoire, ConcurrentDictionary<Guid, Game>) enregistree en Singleton dans le conteneur DI de BattleShip.API. Binds: CAP-1, CAP-2, CAP-3, CAP-6. Prevents: deux collections d'etat distinctes (une par transport) qui divergent. Rule: le endpoint HTTP de creation/consultation et le service gRPC de tir appellent tous deux le meme IGameStore singleton; aucun autre composant ne detient sa propre copie de l'etat de partie.
- (decision) AD-4 Repartition des transports: creation et consultation de partie exposees en HTTP Minimal API (POST /games, GET /games/{id}); l'action de tir (jouer un coup) exposee exclusivement via le service gRPC (BattlefieldService/FireShot), consomme en gRPC-Web depuis Blazor. Binds: CAP-2, CAP-6. Prevents: duplication de la logique/validation du tir sur deux transports paralleles. Rule: aucun endpoint HTTP n'accepte de tir; le service gRPC est le point d'entree unique pour cette action, et les deux transports delegated au meme service applicatif (GameService) qui appelle le domaine.
- (decision) AD-5 Emplacement de la validation: les validateurs FluentValidation (CreateGameRequestValidator, FireShotRequestValidator) vivent dans BattleShip.API et s'executent avant tout appel au domaine, sur HTTP comme sur gRPC. Le domaine garde ses propres gardes (exceptions sur invariants violes) independamment de FluentValidation. Binds: CAP-7. Prevents: validation dispersee inline dans les lambdas d'endpoints, domaine qui ferait confiance a une entree non verifiee. Rule: chaque point d'entree public (endpoint HTTP, methode gRPC) appelle son validateur avant d'invoquer le domaine; les methodes du domaine restent sures meme appelees directement (tests unitaires).
- (decision) AD-6 Strategie adverse: interface unique IOpponentStrategy avec deux implementations EasyOpponentStrategy (tir aleatoire) et HardOpponentStrategy (hunt & target, parite damier), selection par un parametre Difficulty a la creation de partie. Binds: CAP-4, CAP-12. Prevents: branchement de difficulte disperse par if/else dans le moteur, ou moteurs dupliques. Rule: ajouter une difficulte = ajouter une implementation de IOpponentStrategy, jamais modifier la boucle de jeu existante.
- (decision) AD-7 Organisation des tests: BattleShip.Tests reste un projet unique avec deux dossiers Unit/ (tests purs du domaine, ne referencent que BattleShip.Models) et Integration/ (WebApplicationFactory<Program> contre BattleShip.API, HTTP et gRPC in-process). Binds: CAP-8. Prevents: creation d'un projet de test supplementaire non prevu par le socle impose (4 projets), ambiguite sur ou placer un nouveau test. Rule: un test de regle de jeu pure va dans Unit/, tout test qui traverse HTTP/gRPC va dans Integration/.

- (decision) AD-2 (amende) Vehicule des deux vues: GameStateDto composite (HTTP GET /games/{id}) porte OwnGrid (navires du joueur) + OpponentGrid (touche/rate/coule uniquement) dans une seule reponse. La reponse gRPC FireShot (ShotTurnReply) ne porte PAS les grilles completes, seulement le resultat du/des tirs de ce tour + le statut de partie (InProgress/Won/Lost); le client HTTP-GET l'etat complet apres coup si besoin. Prevents: deux implementations qui inventent chacune leur forme de reponse.
- (decision) AD-3 (amende) Concurrence: IGameStore n'expose pas Get/Set brut mais une methode atomique Mutate(Guid gameId, Action<Game> mutation) qui synchronise l'acces a l'agregat Game (verrou par partie). GameService (nouveau composant, seul appelant autorise de IGameStore) est le seul point d'entree pour lire/muter une partie; Endpoints HTTP et service gRPC n'accedent jamais directement a IGameStore. Prevents: double application d'un tir ou lecture partielle (torn read) sous appels concurrents; ambiguite sur qui detient IGameStore.
- (decision) AD-4 (amende) Contrat du tour de jeu: FireShot (gRPC) resout en UNE seule requete le tir du joueur PUIS, si la partie n'est pas terminee, la riposte immediate de l'ordinateur; ShotTurnReply porte les DEUX resultats (tir joueur: touche/rate/coule + tir ordinateur: coordonnee+resultat, absent si partie terminee apres le tir joueur) et le statut de partie. Prevents: ambiguite sur comment/quand l'IA joue son tour (mecanisme separe non defini).
- (decision) AD-9 Source et partage du contrat gRPC: battlefield.proto vit dans un dossier Protos/ a la racine du depot (hors des 4 projets), inclus par chemin relatif (<Protobuf Include="../Protos/battlefield.proto" GrpcServices="Server"/> cote API, GrpcServices="Client" cote App) - jamais via ProjectReference (etend AD-8). Les messages protobuf generes sont l'UNIQUE contrat de l'action tir; les DTOs C# de BattleShip.Models/Contracts sont l'UNIQUE contrat HTTP. Binds: CAP-2, CAP-6. Prevents: un type partage ambigu entre les deux transports (le POCO FireShotRequest initialement place dans Models etait un doublon non resolu du message protobuf - retire).
- (decision) AD-10 Identite des camps: remplace la convention PlayerId:Guid (orpheline, jamais utilisee) par un enum Side { Human, Computer }, utilise dans Shot.Side (historique CAP-10), les DTOs de statistiques par camp (CAP-11) et le domaine. Pas d'identite joueur individuelle: le jeu est solo contre l'ordinateur (non-goal multijoueur du spec). GameId (Guid) reste le seul identifiant du domaine. Binds: CAP-1, CAP-10, CAP-11. Prevents: notion d'identite joueur multi-utilisateur non justifiee par le perimetre, ou implementee incompatiblement (Guid genere cote client vs serveur).
- (decision) AD-11 Mapping des codes d'erreur gRPC: coordonnee hors grille -> InvalidArgument; case deja jouee -> FailedPrecondition; GameId inconnu -> NotFound; tir apres fin de partie -> FailedPrecondition. Binds: CAP-6, CAP-7. Prevents: le client Blazor interprete differemment la meme erreur selon qui a implemente le service gRPC.
